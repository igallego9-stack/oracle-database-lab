Lab 1 — Preguntas de comprobación (Sección 8)
1. ¿Cuál es la diferencia entre Working Directory, Staging Area y Local Repository? Da un ejemplo de un archivo pasando por las tres.
En mi caso lo vi clarísimo con README.md: primero lo creé con touch y ahí solo existía en mi Working Directory, en el disco, sin que Git supiera nada de él salvo que aparecía como "untracked" en git status. Cuando hice git add README.md, pasó al Staging Area, y git status empezó a mostrarlo bajo "Changes to be committed" en vez de "Untracked files". Por último, al ejecutar git commit -m "docs: add initial project documentation", ese contenido quedó grabado para siempre en el Local Repository (dentro de .git), y git log ya lo mostraba como el commit a2b9beb.

2. Si modificas un archivo pero no haces git add, ¿aparece ese cambio en tu próximo commit? Explica por qué.
Lo comprobé sin querer con docs/customer-schema.md: lo creé con echo y lancé directamente git commit -m "docs: add customer schema notes" sin hacer git add antes, y Git me respondió "nothing added to commit but untracked files present". Es decir, el archivo seguía solo en mi Working Directory y el commit no incluyó nada, porque git commit únicamente empaqueta lo que ya está en el Staging Area, no lo que hay suelto en la carpeta.

3. ¿Por qué git status no mostraba las carpetas vacías que creaste en la Parte C? ¿Qué truco usamos para solucionarlo?
Cuando hice mkdir -p database/schema database/migrations ... y el resto de carpetas vacías, git status no mostró absolutamente nada nuevo, seguía diciendo "nothing to commit". Esto es porque Git no versiona carpetas, solo archivos, así que una carpeta sin contenido es invisible para él. El truco que usé fue meter un archivo .gitkeep dentro de cada una con touch runbooks/.gitkeep playbooks/.gitkeep database/schema/.gitkeep ...; en cuanto dejaron de estar vacías, git status empezó a listarlas como "Untracked files".

4. Explica con tus palabras qué es HEAD.
Lo vi en cada git log, donde siempre aparece la etiqueta (HEAD -> main) o (HEAD -> feature/customer-search) pegada al último commit de la rama en la que estoy. Para mí HEAD es simplemente el puntero que marca "dónde estoy parado ahora mismo" en el historial; cuando hice git switch -c fix/readme-title HEAD saltó a esa rama nueva, y cada git commit que hice después movía HEAD hacia adelante junto con la rama activa.

5. ¿Qué diferencia hay entre crear una branch con git switch -c y crear una carpeta nueva con mkdir? ¿Cómo lo comprobamos en la Parte G?
La diferencia la vi al crear feature/customer-search con git switch -c: el prompt cambió de (master) a (feature/customer-search) y git branch la listó junto a master. Eso es una línea de desarrollo dentro del historial de Git, con sus propios commits. En cambio, cuando usé mkdir -p database/schema database/migrations..., esas carpetas no aparecieron nunca en git branch ni cambiaron el nombre de mi rama activa: son solo estructura de archivos en el disco, sin ninguna relación con el control de versiones.

6. Durante el conflicto de la Parte H, ¿qué representaba el contenido entre <<<<<<< HEAD y =======? ¿Y entre ======= y >>>>>>>?
Esto me pasó de verdad al hacer git merge fix/readme-subtitle estando en main: Git me avisó "CONFLICT (content): Merge conflict in README.md". Entre <<<<<<< HEAD y ======= tenía la versión de la línea que ya estaba en main (la que había llegado con el merge fast-forward de fix/readme-title, "Training Edition"), y entre ======= y >>>>>>> fix/readme-subtitle tenía la versión de la otra rama ("Academic Version"). Tuve que decidir yo cómo dejar la línea final, y acabé combinando ambas en "Oracle Database Lab (Training Edition – Academic Version)", tal como se ve en el cat README.md después del merge commit a72e18d.

7. ¿Por qué NO se debe hacer git commit --amend sobre un commit que ya se subió con git push?
Usé git commit --amend -m "docs: fix typo in schema notes" para corregir el mensaje del commit 3bb7be3 (que tenía el typo "dcos: fxi typo") y convertirlo en d59c554, pero lo hice antes de subir nada a GitHub. Si ese commit ya se hubiera subido con git push, amend habría generado un hash nuevo distinto al que ya está en el remoto, y me habría quedado con un historial local que no coincide con el remoto, obligándome a forzar el push y arriesgándome a pisar el trabajo de otro si alguien más ya se hubiera bajado ese commit.

8. Si borras por accidente la carpeta .git de tu proyecto, ¿qué se pierde exactamente? ¿Se pierde también el código fuente que está en el disco?
En mi repo, .git es la carpeta que vi crearse justo después de git init ("Initialized empty Git repository in C:/Users/Irene/oracle-database-lab/.git/"). Si la borrara, perdería todos mis commits (los tres iniciales, el amend, las ramas, el merge conflictivo que resolví), o sea, todo el historial de versiones. Pero el código que tengo en el disco en ese instante, como README.md o docs/customer-schema.md, seguiría ahí físicamente; simplemente la carpeta dejaría de ser un repositorio Git.

9. Explica con tus propias palabras la diferencia entre Git y GitHub, sin usar la palabra "nube".
En mi práctica usé Git desde el principio en local (init, commits, branches, merges) sin necesitar internet para nada de eso. Solo cuando quise compartir el trabajo hice git remote add origin https://github.com/igallego9-stack/oracle-database-lab.git y git push -u origin main, que me pidió autenticarme en el navegador. Ahí entró en juego GitHub: es la plataforma donde subí mi repositorio para tenerlo accesible y poder generar pull requests (de hecho, al hacer push de fix/readme-title y fix/readme-subtitle, GitHub me devolvió enlaces del tipo "Create a pull request for..."). Git es la herramienta que gestiona el historial en mi máquina; GitHub es donde alojo y comparto ese repositorio.

10. ¿Por qué no se debe subir un archivo .env con contraseñas reales a un repositorio, aunque el repositorio sea privado?
Aunque el repositorio oracle-database-lab sea privado, si algún día lo hago público sin darme cuenta, invito a un compañero, o simplemente lo comparto en clase, cualquier contraseña real que haya subido en algún commit seguiría estando en el historial aunque después la borre del archivo, porque Git guarda todas las versiones anteriores (como vi con git log mostrando cada commit intacto). Por eso nunca metería credenciales reales, solo un .env.example con valores ficticios.

11. Un compañero te dice: "hice push y ahora GitHub me rechaza el segundo push con 'non-fastforward'". ¿Qué ha ocurrido probablemente y qué comando ejecutarías primero?
Esto es justo lo contrario de lo que me pasó con fix/readme-title, que se fusionó en fast-forward porque main no se había movido. Si un compañero recibe "non-fastforward" al hacer push, significa que alguien más ya subió commits al remoto que él no tiene en su copia local, así que su rama y la del remoto han divergido. Lo primero que le diría que ejecute es git pull para traer e integrar esos cambios remotos antes de volver a intentar el push.

12. ¿Qué tipo de Conventional Commit (feat, fix, docs, test…) usarías para: añadir un índice de rendimiento a una tabla, corregir una restricción mal definida, y actualizar el README?
Siguiendo el estilo que usé yo mismo en mis commits (docs: add initial project documentation, docs: add customer schema notes, docs: rename project title...): añadir un índice de rendimiento a una tabla lo etiquetaría como perf (o feat si se ve como una mejora nueva de la base de datos); corregir una restricción mal definida sería fix, porque arregla un error real, igual que si hubiera necesitado corregir de verdad mi typo "dcos: fxi typo"; y actualizar el README, como hice yo varias veces, es docs.
